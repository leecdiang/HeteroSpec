# When to rent a stronger GPU

Do not rent solely to add a more expensive model name to the table. First finish the two local studies and decide whether the supported claim is operator packing, useful local cut placement, or structure-aware policy selection.

A third-host replication becomes worthwhile when the local result has: (1) an actual admitted cache lifecycle and natural opportunity census; (2) full numerical qualification; (3) a practically meaningful effect against WB-rechunk or an informative predictive boundary; and (4) a compact source/build/raw fixture that no longer relies on unexported source-host files.

The rental study should then freeze the same Qwen3-8B Q8 target, actual cache semantics, tokenizer and held-out root IDs, with the third device's own original reference. Run QB, WB-cut, WB-rechunk and the frozen transferred selector; do not retune it on that test panel. Report a second, separately labeled locally calibrated policy only if its calibration was preregistered and charged. Use the existing ordinary workload before adding speculative depth, concurrent serving or longer context.

Choose the GPU/OS/driver only after checking source compatibility and required memory. A data-center GPU tests transfer beyond laptop CUDA; its larger memory must not silently change weight precision, context, residency or reference. A new Linux/CUDA runtime is itself a deployment change and needs new qualification. A faster card can shrink launch-bound savings; this is a result, not a failed rental.

No vendor, price, billing commitment or paid account action is selected here. Reserve the budget after the local decision and an actual reproducibility smoke. Third-host speed alone does not cure a weak novelty or application argument.
