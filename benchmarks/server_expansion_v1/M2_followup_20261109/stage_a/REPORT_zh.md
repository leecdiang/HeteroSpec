# PR210 零 GPU 阶段结论

Stage A 已完成。没有编译、执行模型、创建 CUDA 上下文或消耗新的 native 请求；没有修改旧实现、基线、结果、协议和论文。Stage B–E 与32B GPU分支未启动。

12个实际生成源码文件已按原模板和固定 transform 逐字节重建，匹配编译清单；loop4、packed、标量R三个现存ELF及相关库文件哈希匹配保存记录。模型SHA沿用原生运行时已核验的完整绑定，本次仅核对文件大小，未重新遍历权重。重启后的文件身份核查不等于新的GPU数值资格。

144条保存的计时/预热记录、原live/replay结果和三版本完整成本表复算通过。LOCAL-packed 的8条live请求，k7比k3增加1.669811秒：

|组成|增加秒数|
|---|---:|
|target prefill|0.003388|
|target verify|0.629439|
|draft阶段|0.681317|
|未分配residual|0.355665|

其中输出拷贝字段增加0.017493秒，已经包含在residual中，不能再相加。该字段包含getter、所有权拷贝及其中的分配；其余批次准备、采样、元数据、同步等没有独立完整归因。**residual不能叫日志开销**：回执文件写入和fsync发生在service计时结束后。源代码中的in-memory JSON操作仍在service内，两者须区分。

关键源码判断：

- 全词表输出复制到自有向量，decode返回后可用，下一次decode/reset可能修改它们。未来q4pair必须保留第一批4行，不能只返回第二批。
- GCC11的已绑定实现会在稳定宽度下保留内层vector容量。不能看到`outputs.assign`就认定每轮全量malloc；reset/clear和尺寸变化仍有边界成本，但未单独测量。
- getter会调用同步，显式decode同步也存在。按源码和保存计数推导的调用位置由3516增至4188，**这不是实测CUDA等待或kernel launch数**。不能仅凭这个数字删同步。
- 最后一轮draft前向承担完整接受路径的KV物化。删除它、缩短近cap提案或跳过draft状态更新均不是本轮可直接做的无语义优化。
- 有限值检查/argmax与批次、元数据操作可列为后续profiling假设，本阶段没有证明可移除热点足以改变宽度选择。

对未接受提案重新分账，避免把未比较后缀全叫错误token：

|live LOCAL-packed|k3|k7|
|---|---:|---:|
|第一次实际比较失败|58|74|
|拒绝后未比较后缀|62|262|
|接受时触及cap的未消费后缀|8|16|
|总未接受提案|128|352|

VERIFY行数从1152增至1376。按保存轨迹核算，每行verify时间反而下降约5.04%（live）/3.91%（replay）；轨迹和位置不同，不能把它当等工作量q8效率结果。当前证据支持“更多实际工作抵消批量收益”的描述，不能据此归罪draft模型质量变化。

**Stage B的固定输入尚不齐备。** 248+8需要256个已知token，252+8需要260个。四条冻结流长度依次为199、196、278、197；三个根分别还缺61、64、63个token，第一预定计时根也不足。按协议不能静默补齐、换根或伪造跨界。

如将来继续B，须先明确登记：按不变R扩展continuation及精确oracle/bridge成本，或修订origin设计。不能预设扩展不会提前EOG，也不能假定24条参考余量必然足够。此次0GPU任务没有准入B，也没有批准任何新的GPU窗口。

累计预算仍为1826/2048请求、3021131/8000000预留行，余222请求、4978869行。旧失败仍计账。没有新的资格或性能结论改变原有限范围的k3建议，亦未证明未来共同优化一定无效。
