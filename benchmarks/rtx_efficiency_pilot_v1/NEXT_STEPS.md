# A bounded implementation direction after the speed screen

The next intended contribution is a verifier that preserves the frozen target-only output while retaining batched execution's measured latency advantage. A new invariant, portable decision rule or measured implementation gain is still unproved. The 300-request screen justifies one prototype, not a publication-readiness claim.

First budget: two working days for diagnosis and one isolated CUDA/runtime prototype. Stop if the cause cannot be distinguished within that budget; do not keep accumulating trajectories. Do not change the currently integrated manuscript or historical reference to make a candidate pass.

1. Freeze a deployment reference and isolate the first failing state. Use /2 position11, /5 position87 and /6 position21 (zero-based committed output indices), plus passing /3. Capture a live common prefix/KV state and pending logits once for diagnosis; qualify restoration with a sham before changing execution. Existing whole-context transfers are paid diagnostic operations, excluded from any online acceleration claim. Compare scalar target evaluation and native batched verification on the same input positions, masks and proposals. Record first operator discrepancy, top-two margins and retained-state validity. No causal attribution from final trajectory agreement alone.

2. Implement the smallest change justified by those observations. If reduction schedules change the ranking, keep row reduction/quantization rules consistent for the affected operation while computing multiple verification rows in parallel. If state/mask/rollback is responsible, repair that logic while retaining target batching. The preference is an operation-level or state-level repair with bounded overhead. Current data do not show which repair is correct; full serialization is only a diagnostic control. Any selective uncertainty fallback needs a justified error criterion, paid replay cost and state qualification; an empirical margin threshold is not a universal guarantee.

3. Measure the integrated native method against a fixed reference. It must repair all exposed /2,/5,/6 cases in all repeats and retain correct passing cases, then run an exposure-audited additional HumanEval/MBPP panel at a frozen cap and context. Compare fully configured target-only, fixed k2/k4, ngram, native cascade and applicable existing deterministic-verification/batch-invariant approaches. No task-label policy, answer oracle, reference pre-execution or changed output lengths. Include proposal, synchronization, retry, cache and rollback costs. A meaningful first gate is >=20% lower full resident-request latency than the fastest qualified baseline with no observed output/stop mismatch on the frozen panel. This is an engineering gate, not a mathematical guarantee from finite tests.

4. Only then test portability: at least another model/quantization and one other backend/hardware path, with the same deployment reference definition and measured configuration costs. GPU-specific kernel tuning alone may be an engineering contribution; a stronger paper needs evidence for the cross-case principle and a clear difference from existing work.

Novelty pressure is explicit. Thinking Machines already provides batch-invariant operations; LLM-42 already uses fixed-shape verify/rollback; SpecDec++ and Learning to Draft already adapt candidate lengths or directly optimize drafting/verification efficiency. A sufficient increment would need a demonstrated cheaper consistency mechanism in the quantized consumer-GPU setting plus a transferable condition for when it is useful. The screen has not established that increment. If the prototype only recreates an existing mechanism without measured advantage, close this as a useful runtime investigation.

No runtime patch, causal same-state fork, selective replay policy, portability check or prospective holdout was executed in this PR. All measurements in `REPORT.md` use existing released native methods.
