# RTX Round 1: a bounded executor decision

Deployment: one Windows RTX 5070 Ti Laptop GPU (12,227 MiB), a resident Q8_0 target and draft under the existing Windows full requested-logit, dense F16-KV contract. This round evaluates an execution mechanism, rather than changing the reference or speculative acceptance rule. An eventual service application must have enough eligible eight-row projection work to pay for admission, planning, synchronization, reconciliation and fallback.

The bottleneck hypothesis is repeated projection weight-fragment loading and launch overhead. Existing backend-loop4 quantizes eight activation rows once and launches two native four-column kernels. Current packed also quantizes once, but launches both groups on a single grid with separate CTAs. Candidate C retains the original four-column K partition and reduction, placing two independent four-column accumulator groups in the same CTA and explicitly reusing each loaded weight fragment. Native width eight is a different numerical recipe and is excluded. A→B measures launch/grid changes; B→C measures the additional mechanism together with its register/shared-memory/parallelism cost. DRAM/L2 effects remain unknown without counters.

The primary endpoint is complete same-request resident service wall time, including reset, prefill, draft, verify, host planning/guards, necessary synchronization, reconciliation and fallback. The measured parent interval is authoritative; overlapping child intervals must not be added. Kernel-only and quantize-plus-synchronize operator timing are separate diagnostics. A latency gain is useful only if full outputs and active target/draft state remain qualified and request-level eligible work leaves credible net savings.

Main controls are backend-loop4, current packed and the strongest eligible fixed strategy selected only on development requests, then frozen before any held-out service measurement. Lazy-tail/cap repairs and buffer reuse must be identical wherever applicable. A real target-only/runtime is an application-context control; if numerical semantics differ, it is excluded from exact-contract attribution. The previously reported roughly 11–25% speculative gain over target-only is background, not this mechanism's increment. Prior A5000 strong-control reductions of 1.08–2.01% and #213's k7 loss are different panels and are not RTX predictions or pieces of a cost stack.

Correctness precedes timing: complete vectors and untrimmed/trimmed state, actual descriptors/dispatch/placement, native geometry, build/model/module identities and graph-reuse obligations must be checked with non-assert failures. The 22 #221 cases are frozen separately for A/B/C. Pre-execution rejection, independently qualified fallback and post-execution owner invalidation are distinct outcomes. Capture-only observations cannot certify clean execution.

Request closure requires a real k3 all-accept bonus to become the next seed, a fifth-proposal rejection consuming L4, then correction/trim/pending and a real continuation, preserving all originally requested outputs and CAP/EOG semantics. A constructed CPU fixture is state-machine preparation only. A q32 capture's first eight activation columns is a derived real-operand fixture, not a captured q8 native descriptor.

Decision: GO only after qualification, interpretable paired improvement over packed, real-request coverage and plausible complete-service net benefit. A decisive failure is NO-GO; missing access/identity/coverage/cost evidence is INCONCLUSIVE. Do not increase samples to chase a positive sign. No #213 live panel or #215 supplement is rerun.
