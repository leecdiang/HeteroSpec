# 转交 B570 平台的执行指令

请执行本 PR 的 `benchmarks/b570_cpu8_closeout_v6/PROTOCOL.md`。这是以 PR119 `aa7d64b5e4c198699a2f1fcc52c8ff2e31103fa7` 为证据基线的新任务；旧 UUID 永久关闭，旧失败、PR115/117/119 不覆盖。保持 Draft，不合并。

本轮目标只有 CPU8 闭环，不运行 GPU、模型、actor 或 RTL。先落实两项修复：

1. 原根 live 验收必须执行当前预算/存储检查；任何 relocated/reconstruct 路径只能返回 RECONSTRUCTION_ONLY，不能产生验收 PASS。
2. 下载与隔离复算必须绑定真实工具请求、响应、会话终态和输出字节；声明性 receipt 不能证明执行。复用原 watchdog 的 tool binding，保留真实 provider 回执，不能伪造外部认证。

新增 admission.py 只是便携原型，Linux 八项单元测试不代表 Windows 资格。请接入真实原生审计器、文件系统身份检查、预算运行时监督和冻结清单，不能从输入 JSON 读取几个 True 就判 PASS。下载 helper 仅核验字节身份，仍须实现真实下载回执绑定。

开发与最终复审必须给正式八项预留至少 3,600 累计进程秒、给交付再预留至少 3,600；正式阶段与交付各预留至少 1,800 墙钟秒。全轮累计限额保持 21,600 秒，不随阶段重置。先估算八项和远端恢复的真实上界，必要时提高预留、压缩开发额度。每次工具调用前确认完整操作及清理的可执行预算，运行中强制守住预留；没有可强制上界就不启动。不要再次用重复短超时复审耗光正式执行额度。

在新 UUID 完成部署、必要原生门槛、针对性负例、真实下载/恢复正例，取得针对最终实际源码的 scoped clean 复审后冻结。按协议顺序正式八项各执行一次，正确故障检测和进程清理均满足才算通过；异常正式失败保留并停止，不科学重试。小路径/工具适配/分块参数问题可在冻结前自主修复并记录，不因这些问题停下来反复询问。

八项通过而交付未完成时报告 CPU8_CASES_PASS_DELIVERY_PENDING，使用交付预留完成真实远端恢复；不要重跑八项。只有所有原有 native/raw/freeze/live/delivery 条件全部满足才报告 CPU8_INTEGRATION_PASS。预算不足以完成开发复审时提前封存具体修复和阻塞点，不能挪用正式预留或伪造 clean。

结果回推本 PR：完整逐项表、当前/封存预算、真实工具回执、归档与远端恢复哈希、已知进程覆盖和 UNKNOWN、源码与二进制对应状态。明确这是工程集成资格，不是 B570 性能或硬件收益结论。
