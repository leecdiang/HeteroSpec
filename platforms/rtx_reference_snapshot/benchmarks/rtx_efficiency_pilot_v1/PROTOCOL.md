# RTX efficiency screening pilot

This is an exploratory exposed-task pilot, not a held-out evaluation or a new-method claim. No manuscript or existing runtime is modified. Freeze the runner, input prompts and this protocol in a local Git commit before execution; every request records that commit.

Use the existing released llama.cpp b10839 (upstream 0cae43063cf15170e91a2ff4d034da0ecef4a1b2), Qwen3-8B-Q8_0 target and Qwen3-0.6B-Q8_0 draft on the RTX 5070 Ti Laptop GPU. All conditions use the same single slot, CUDA full offload, context 2048, logical/physical batches 512, Flash Attention on, f16 KV and deterministic greedy sampler. Inputs to the four HumanEval cases are the original native token IDs. Code-edit cases use the same target chat template with thinking disabled.

Conditions: target-only, released draft-simple k=2, released draft-simple k=4, released ngram-simple lookup=4 and draft=8. The latter is a strong existing cheap-proposal baseline, not our invention. Four exposed HumanEval tasks (15,25,18,99) include known repair, regression, persistent deviation and a control. Two deterministic synthetic code edits probe a workload where prompt lookup may amortize verification. They are reported separately and cannot establish general coding speedup.

Three rounds, one fresh server session per condition per round, reversed/rotated condition order and rotated task order. Each session has one excluded 32-token warm-up. Seventy-two measured requests, twelve warm-ups. Prompt reuse and cache RAM disabled. Serialize GPU access; terminate only the server process created by the runner. Model loading is excluded by a resident-service boundary, but draft compute, draft prefill, target verification, rollback and HTTP request overhead remain in whole-request wall latency. Generation timer is secondary; both prompt and generation timers are retained. No synthetic acceptance flags, answer oracle or instrumentation state transfer.

Qualification: native committed token arrays, length and stop type/word must match the target-only result in every same-round task comparison. Any mismatch disqualifies that task from a strict speedup claim; its raw timing remains diagnostic. Repeatability of target-only is checked separately. Exact equality here is deployment-reference equality under this frozen configuration, not proof against historical UB1/Flash-Attention-off runs, nor a mathematical guarantee on all inputs.

Runtime API binding: `timings.cache_n` is reused prompt-token count; the top-level `tokens_cached` is final stored context length in this revision, not prompt reuse. The first startup attempt incorrectly asserted the latter was zero and stopped after the first target response; preserve its logs as a failed infrastructure attempt, exclude it from measured results, fix the binding and freeze a new commit before restarting into a new directory.

Advance only if a candidate has >=10% lower median total request latency and lower generation latency in an explicitly named workload, all three pairs improve, and every selected case passes equality. Otherwise report no qualified win. Positive results require a bounded second stage with a stronger Flash Attention baseline/configuration, nearby speculation settings and additional inputs. No cherry-picked token/s rates, comparisons on different output lengths or treating low acceptance as numerical evidence. Power/energy not measured; do not claim energy improvement.

An adaptive follow-up may test a concrete identified bottleneck, with a separate frozen protocol and manifest. The initial screen alone supports engineering prioritization, not novelty or journal readiness.
