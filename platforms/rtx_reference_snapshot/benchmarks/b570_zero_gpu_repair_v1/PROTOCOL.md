在任何构建、资产下载、测试和审查子命令前启用外层 CPU 任务账本，记录单调开始/结束、命令身份、PID+创建时间、父子关系、退出与终止结果。已有交互式 Codex/终端及第一次账本引导命令的范围单列，不冒充整机全进程；引导命令起止由外层工具回执保存。此后所有任务发起的子命令及后代均在账本范围，不能把 Git、审查、归档或最终恢复排除。无法观测的进程标记缺失，不补造寿命。实现可用 Job Object/系统进程事件等 CPU 机制；不得仅以父 PID 猜完整进程树。

从 SOURCE_LOCK 读取固定源码并保留字节哈希。复制到新 `host/` 修改，旧路径禁止写入。移植时必须替换旧 common.py 中硬编码的 `C:/hs/b570-paper-support-v1-20261016`；新运行根前瞻登记，启动时拒绝指向旧任务根。原 LauncherCapture.dll 不作为新编译证明。明确实际 Windows/Python/PowerShell/C# 工具链身份，不通过 GPU 查询发现环境。

## E1：先复现与设计，再有限修复

先用 CPU 单独复现 PR115 的共享输出根、槽位 A 关闭后 B 启动、封存区通知及负例提前拦截。保存所有启动/未启动事件，记录本机是否复现；没有复现则写 `NOT_REPRODUCED`，不得宣称已证明唯一根因。故障注入用于检验防护，不冒充自然复现。

先写 `results/DESIGN_DECISION.md`，描述注册槽位状态机、目录拓扑、监控句柄代次、事件序号、封存边界、清理与重新启动路径。每个槽位唯一 ID，状态至少涵盖 PREPARED/ACTIVE/CLOSING/SEALED/FAILED。控制器自身合法目录创建/关闭应有明确责任与窗口，不能与科学写入权限混淆。必要时预建目录、改用持续 watcher 或隔离活动根，但必须保留对注册的封存输出和冻结输入的保护。

通知接收时间不是写入时间；ReadDirectoryChangesW 原始通知没有 writer PID。逐条持久化原 buffer、action/path、接收单调时间、watch ID/代次/根、事件序号、当时槽位注册状态与判断。writer PID/实际操作时间没有独立证据时保留 null。CPU 注入器可记录自身写入 PID/操作区间，但不能把它当作 OS 通知提供的信息。

封存应有生产者及全部写入者结束、流关闭/刷新、pending I/O 处理、审计与状态提交的明确顺序。`CancelIoEx` 发出不等于完成；记录最终 completion 与关闭结果。不得靠固定 sleep、延长宽限期、忽略 action=3、丢弃旧路径事件、仅排空队列或重开句柄宣称建立封存边界。任何无法证明归属的受保护路径变更仍阻止通过。

不要求证明原来事件唯一写入者才能修复，但必须区分 `ROOT_CAUSE_CONFIRMED`、`CONTAINMENT_VALIDATED`、`UNRESOLVED`。第二种需说明替代拓扑如何消除暴露，并通过相同保护测试；不能把取消封存监控作为隔离。

最多 6 个开发修订，每个是前瞻记录哈希的代码状态；每轮最多 2 次完整矩阵和 24 次定向 case，所有尝试计账。可在预算内自主修复、编译、重测，不因每轮结束向作者再次要确认。原 PR115 两轮结果不计入本协议成功率。不得在最终确认失败后返回开发或另挑成功轮。

## E2：强负例与监督完整性

所有写入负例只操作本任务新建的可牺牲 CPU 夹具，模拟冻结输入、封存结果和旧槽位；绝不修改真实固定源码、PR115数据或模型。夹具/活动/封存根与外部日志根分离，避免日志自触发。CPU与未来生产路径共用相同权限与判定函数，不加CPU特许；故障钩子必须显式登记。

每个负例必须依次证明：fixture ready → 注入器实际触发 → 指定控制点到达 → 正确 detector 依据相应对象证据拒绝 → 子进程退出/清理。日志不足、不同路径通知或前置失败不得替代目标故障。状态分为 PASS、NOT_REACHED、WRONG_FAILURE、EVIDENCE_MISSING；suite 只有全部 PASS 才合格。预启动类用例由控制器注入，不强制伪造子进程启动，必须保存预定阶段及拒绝证据。

检测线程可能先记录拒绝、注入线程后记录 ACK，允许这种接收顺序；要求注入的单调操作区间及独立副作用证据与 detector 对应，而非强行排列跨线程接收先后。需确认 detector 后无 GO/新工作，最终确已清理。

日志超限必须有生产者 ACK、完整 FRAME 序号/字节及软硬界；证明达到软界、所有已确认完整帧均保留、受控停止且不超过预留。不能以错误文本包含 `log` 为依据。合成通知丢失只称解析/队列丢失注入，不称真实内核溢出。

运行时资源、活动目录、watcher 各自有独立可重算时间序列：nominal 100ms，严格有效间隔 ≤1,000,000,000ns。记录 armed、循环开始/完成、读取起止、失败、终止覆盖；不以零事件推断 watcher 活着。边界 999,999,999 / 1,000,000,000 / 1,000,000,001ns 分别通过/通过/拒绝，用确定性时钟测试，真实集成另行报告。关闭后审计单独计时，不追填运行期间采样。

心跳/关键证据写入失败应停止资格并清理；由独立外层控制器保留停止回执。若外层也无法保存，结果 EVIDENCE_MISSING，不能通过。辅助进程使用相同真实台账，区分过程墙钟、进程寿命和，嵌套时间不可相加伪装独占开销。

## E3：独立实现审查、冻结与完整确认

在最终确认前完成一次真实独立实现审查，覆盖最终 host 代码、Windows I/O/句柄生命周期、状态机、故障判据、监督和原始审计器。优先仓库既有 OpenAI/Codex 审查能力；设计审查或主执行者自审不能替代。审查单次最多 900 秒，最多 2 次，总额 1800 秒；不得达到旧 300 秒后宣称审查通过。超时、不可用、无最终结论、未处置的实质问题均不准入。修改后须覆盖最终代码哈希，可用有明确基线与范围的增量审查；不可对旧代码的 clean 结论移用到新代码。

冻结 `CONFIRMATION_FREEZE.json`：本协议/矩阵/预算、完整 host+审计器与产物哈希、审查结论与覆盖范围、环境、目录/槽位配置、顺序、资源预留。认证远端同一提交字节；此前没有确认轮。上传/认证也计入账本。

同一冻结版本执行固定 3 轮完整验收，每轮全新控制器/注入器进程和唯一槽位命名；每轮内部保留真实的多槽位共享生命周期，不能通过每 case 全新隔离根规避跨槽位问题。矩阵顺序：第1轮按 JSON 顺序，第2轮逆序，第3轮按 case ID 的 SHA256 升序。不按结果调整顺序；无小时/隔天等待要求。

每轮正常转换 case 完成 8 对 A→B（16 槽位），连续监控封存 A 与活动 B，所有槽位唯一 ID；每次 B 启动前有 A 的封存与关闭证明。专门负例则在 A 已 SEALED 且 B ACTIVE 时由受控注入器修改 A：确已写入并拒绝，不能归为普通跨槽位噪声。

每轮所有矩阵行均 PASS；全部 3 轮一致。任一 case 未到达、错误拒绝或缺证据，该轮和最终验收失败。安全、资源、监控丢失应立即结束相关进程；在全局监督仍可靠时可完成该轮剩余独立诊断 case，但不得开启后续确认轮。所有未启动项显式列出。不重试、不修代码重开确认、不抹掉失败。

## E4：恢复、报告和停止

交付完整原始证据、非循环哈希 manifest、独立 raw auditor 和固定 schema 规范化回执。auditor 必须从 raw 重建，不能读取现成结论作为输入。新空目录实际下载远端归档，逐成员验哈希，执行包内未改审计器，重算结果与发布报告逐字节匹配。最后审计后的收尾 Git/上传/恢复进程也记录：用外层关闭回执封存最终账本尾段，尾段最后确认上传的边界及无法自包含的回执明确说明，不能自我哈希递归或伪称包含未来操作。

ENGINEERING_READY 必须同时满足矩阵、跨槽位生命周期、三条监督流、辅助进程账本、最终实现审查、冻结与真实恢复；任何缺失均 ENGINEERING_BLOCKED。若有超预算，另记 PROTOCOL_VIOLATION，不能用 blocked 掩盖。READY 仅表示此冻结 CPU 监督实现通过该矩阵，不能推出 GPU actor 可用、科学性能、Windows 所有竞态已穷尽或 PR115 已解封。
