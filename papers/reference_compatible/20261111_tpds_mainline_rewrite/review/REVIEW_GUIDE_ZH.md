# HeteroSpec：TPDS 主线重构审阅说明

## 这一版回答什么问题

**怎样在保持一个既定量化部署的计算结果和状态的同时，把已知查询组织起来并行执行？**

正文题目是 **Reference-Compatible Parallel Execution for Quantized LLM Inference**。论证从实际批量执行的数值分歧开始，经过原生算子干预确定需要保留的执行条件，再给出可执行的查询分组和并行构造。实验依次回答结果是否一致、方法各部分贡献多少、完整请求是否获益。

物理范围、算术路径和状态管理共同支撑这一问题。全文集中呈现两个技术贡献：识别兼容并行执行的机制条件；把这些条件落实为跨推理阶段的执行方法。

## 关键结论和收益口径

- 在已记录的 Linux Qwen/Smol 资格验证中，6,740 个完整目标向量和 4,784 个 active-KV 状态比较通过；其他模型、宽度和终止状态的检查在补充材料列出。
- 强 backend-loop4 对照下，Q8 packing 的完整服务增量为 **0.80%–1.64%**。局部切分的收益取决于实际边界机会；自然样本中需要额外 Whole 调用的周期是 **20/2,224**。
- Qwen3-8B、Qwen3-14B 和 Llama-8B 的完整投机应用，相对各自最快的已测固定 target-only 对照，resident service 分别减少 **17.21%、25.54%、11.52%**。这些数字包含投机执行的收益，不用来替代组件归因。
- 八行等量工作实验中，q8 比两个 q4 调用用时少 **3.94%–11.91%**；live k7 请求却因增加草稿和验证工作，比 k3 多用 **13.58%–14.59%** 的完整服务时间。图 6 将两者连成解释。
- 混合 Q4 的已完成全模型服务比较保留原 graph-level scalar-loop 对照。更强 backend-loop 已完成的是算子证据；证据截止时，其全模型 S3 仍在进行。

## 体系结构与并行系统定位

本文的实现载体是运行时软件，其研究对象是硬件相关的执行组织：query width 如何改变激活量化、归约组织、原生 dispatch 和 CPU/GPU placement；怎样保留组内计算，并把独立的组暴露给 GPU。Whole/Local 的比较进一步解释物理范围边界、外层图宽度与实际成本的联系。CUDA 与 Vulkan 的差异进入机制和方法本身，而不只出现在平台列表中。
