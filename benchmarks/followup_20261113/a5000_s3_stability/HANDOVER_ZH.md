# A5000 后续实验交接

本 PR 仅设计，不启动模型/GPU。目标是验证同一强对照收益的稳定性，而不是继续寻找大于5%的结果。

## 执行顺序
1. 先在服务器只读确认原 S3 数值产物、模型、native reader 和所需输入是否仍存在。原数据经过清理，不能因为历史报告说“可读”就假定现在仍可读。若缺少关键资格参考，按 README 生成新的独立 R，不重写旧结果。
2. CPU 阶段绑定原 B/C 能力、计时区间和实际启动命令，适配 successor runner。原 plan/run 写死了 GBC/423，不可直接当作新方案运行。保持原 STATE、账本、源代码和旧预算不变。
3. 原12 roots定义 R；两个新日期各完成平衡的B/C配对。另一个 H cohort 选12个新短prompt，输入选择完成后才生成输出。不要把 R 与 H 混合成一个“最佳收益”。
4. 提交实际资源清单、输入列表、日期、预算及保留方案，取得本轮执行批准后才启动。此前任何旧实验批准不自动转移。
5. 资格通过后按冻结计划运行。可修复普通CPU准备错误，不要因为路径/换行/归档错误发明新的门控层。数值错误、未知活跃任务和资源冲突仍需停止相应步骤。
6. 正负结果同等交付。两日期只给“这两次会话条件下”的估计；不假装获得跨日期总体分布。

## 本次实际验证
CPU schedule.py在Python3.12执行 --self-test 通过：R96正式workers、H48正式workers，分别192/96 warm+measured请求，配对和反向顺序检查通过。另以 python -O 生成 R schedule 成功；这仅验证计划生成，不是 -O 下断言测试，更不是native runner测试。

仍未完成：服务器在线资源检查、真实native adapter、执行授权、R/H原生资格、计时。所有GPU结果为 NOT_RUN。

## 建议交付
- 每日期、每root的B/C时间比；root等权主估计和明确条件化区间；
- 原S3/新日期/新输入分面，不跨面板混合；
- prefill/decode/完整worker和温度时钟摘要，全部失败/重试与消耗；
- 无新GPU收益时直接说明，不扩大样本直到显著；
- 一页论文结论影响说明：增强稳定性、否定稳定性或仍不确定。

详细数字、停止条件和统计口径以 README.md 为准。
