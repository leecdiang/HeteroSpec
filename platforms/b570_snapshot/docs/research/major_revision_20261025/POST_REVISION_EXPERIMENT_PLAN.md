# 大修后的最小补充实验：同一运行时内连接 resident 与 fresh 服务结果

**状态：NOT EXECUTED。** 本文是作者实验计划，不是论文结果或补充材料。未启动 GPU、模型加载或新计时。先完成正文重构和现有数据补充，再执行下述可行性检查；通过后才冻结确认性实验。

## 1. 只解决一个问题

现有 resident、k=3 结果显示 QB 相对 PQ 有增益；后续 fresh、k=1 面板没有建立实际增益。两组还改变了驱动、输入、计时边界和参考，不能把差异归因于 context 创建或 CUDA Graph。

下一实验在同一主机、驱动、模型、输入和参考下，只交叉改变 **draft 长度 k（1/3）** 与 **context 生命周期（resident/fresh）**，测量 QB 相对 PQ 的总成本效应。它回答“改变这两个部署因素是否改变 QB 的价值”，不扩展到跨 GPU、跨模型或未见输入的泛化。

**暂不增加 B570 实验、模型家族或完整长上下文套件。** 同一桥接实验足以决定论文是否能从两个分离的观察推进到受控的部署解释。

## 2. 先完成工程前提，不计作新实验

发布可审阅的最小运行时材料：固定上游提交、PQ/QB 补丁、构建命令与依赖、实际二进制及模型/tokenizer 哈希、布局/phase/cache dispatch 测试、一个可分发的相同输入 replay fixture、原始计时 schema 与分析脚本。只含论文表格的重建包不满足这一前提。

建立 `BRIDGE_FREEZE.json`。以下字段缺失、与实物不符或指向浮动版本时，启动器直接拒绝运行：

- RTX 主机和电源/性能策略、线程数、设备占用检查、目标/草稿模型与 tokenizer 文件哈希。
- 12 个输入的原文、格式化后字节与 token IDs、采样和 EOG 规则、输出 cap、KV 类型、context 与 batch 容量、禁用 prompt-cache reuse 的配置。
- R、k=1 PQ、k=3 PQ 的参考文件哈希，以及三个时间边界、warmup、排序表、计数器实现和观察模式。

## 3. 固定输入与四个部署单元

先做 Qwen3-8B / Qwen3-0.6B，均为现有 Q8_0 文件。沿用原 12 输入：

| 来源 | 固定 ID |
|---|---|
| sanitized MBPP | 123、140、255、401、413、418 |
| GSM8K/test | 111、120、1308、141、322、443 |

采用一个共同的新驱动；全单元使用相同 prompt 格式、context1024、目标 caller UB4、draft UB1、F16 KV、non-flash attention、24 host threads、greedy sampler、native EOG 或 cap128。cap128 是本桥接实验的共同设置，不能宣称恢复了所有历史实验细节。完整输入 manifest 必须在启动前冻结。

| 单元 | k | context 生命周期 |
|---|---:|---|
| A | 1 | resident |
| B | 3 | resident |
| C | 1 | fresh |
| D | 3 | fresh |

每个单元均测量 **PQ_A、PQ_B、QB**。PQ_A 与 PQ_B 运行完全相同的实现，是 A/A 控制。每次只有一个请求在执行。

- **Resident：** 每个臂持有独立 context 和 graph cache，先完成登记的初始化；随后复用 context。每次计时从正常请求状态清理/重置开始，包含完整 prefill 和生成。不得复用上一输入的 KV 或前缀。
- **Fresh：** 模型权重仍驻留，但每个请求重新创建/reserve context，并在计时结束前销毁。输入、prefill、生成、状态处理和结果对象构造与 resident 使用同一路径。
- 两种生命周期都保持正常的进程级驱动状态；fresh 不是冷启动 GPU。context 生命周期带来的图创建、cache 保留和分配成本属于被测因素，不通过计时后扣除消掉。

## 4. 先做有上限的可行性与观察器检查

### 4.1 参考与工作资格

先封存 12 个 target-only R 端点，以及两个 k 下各 12 个 PQ 参考请求。不同 k 的内部 trace 可以不同；二者最终 token 序列和停止行为都必须匹配同一 R。

随后对全部 12 输入 × 4 单元 × 3 臂完成一次资格运行。相同 k 下，PQ_A/PQ_B/QB 的完整端点、target/draft logits（含拒绝或丢弃行）、accept/correct/bonus 决策、KV trimming 和 cycle/state trace 必须匹配。跨 lifecycle 也须保持相同 k 的工作轨迹。记录每层实际 q、物理 key extent、mask/stride 和 graph identity；不得只用 caller 的 k 推断物理执行。任何失败都保留为该单元的资格失败，不能删除输入后重新命名为完整面板。

### 4.2 CUDA Graph 的实际状态

逐请求记录 capture 尝试/成功/失败、实例化、replay 次数、eager/fallback 次数与原因、cache hit/miss/失效、图节点数和 shape identity。不得把“编译时启用”或“设置 ON”写成实际 replay。诊断不得插入 operator readback、额外同步或拆开自然图。

优先采用内存缓冲的原生分支计数，计时后写出记录；**不假定计数递增免费**。预先选定 GSM8K/443 与 MBPP/413，在两个可行性进程中，对四单元完成相同 PQ 的 counter-on/off A/A 校准，固定 64 次校准请求。检查输出、图选择和同步结构是否保持一致，并报告观察开销及其不确定性。校准的工程预算为 0.5%（实际阈值的四分之一），不是已知开销或功效结论。

若校准不能支持该开销预算，主计时使用关闭观察器的路径，Graph 记录来自同身份的独立诊断运行；论文只报告后者的观察结果。若实际 capture/replay/fallback 无法可靠辨认，仍可登记纯总成本比较，但 **Graph 解释停留在观察假设，不能声称已得到有效 Graph 因果对比**。可行性结束时在 manifest 中固定采用哪种模式，不能看确认性速度结果后切换。

## 5. 固定确认性预算与执行顺序

固定 **8 个全新进程会话，至少 4 个预登记日期，每日不超过 2 个**；同日会话间隔至少一小时。日期/时段与会话编号在首次确认性执行前列入 schedule，不按早期结果增减会话。

每会话完成 12 输入 × 4 单元 × 3 臂，即 **144 个计时请求；合计 1,152 个**。每个 input/cell/arm 先做一个登记的完整 warmup，合计另记 1,152 个 warmup 请求。Resident warmup 后保留 context、执行正常请求重置；fresh warmup 的 context 已销毁。预热、资格、参考和计时请求分别计数、分别记账。

排序生成器固定种子 `20261025`。先生成并保存 CSV：12 输入按会话轮转；四单元按预定 Latin-square 顺序轮转；每个 input/cell 块先按登记的三臂顺序 warmup 一轮，再按预登记的均衡顺序计时一轮。三臂的六种排列在完整实验中均衡轮换。种子控制顺序，不给 greedy 输出引入随机性。保存实际执行顺序和每个开始/结束时间。

八会话是资源预算，**不是声称已经达到 80%/90% 功效的样本量**。可行性不用于挑选有利效应或把快的输入移入主面板。

只允许在科学槽位开始前因身份、设备占用或启动失败重试。开始后出现的超时、退出、错误输出、计数不符或环境告警按预登记规则标记；不以“慢”定义失败、不静默替换。有效数据不足时报告未完成结果。修复后重跑需要新协议版本，原记录保留。

## 6. 计时与分析

### 6.1 三个预先定义的成本边界

1. **主指标：完整请求服务时间。** 从开始处理该请求前，到返回完整结果并完成该生命周期要求的状态处理/同步/销毁后。包括 tokenizer/输入准备和结果对象构造；reference 字节比较与文件输出放在计时之后。
2. **共同内部窗口：prefill + generation。** 两种生命周期内使用相同代码位置取时间，辅助判断生命周期工作在总差异中的位置。它不能取代主指标。
3. **生命周期包围窗口。** 分别记录 create/reserve、正常状态重置、destroy 等真实区间。重叠区间不强行相加成 GPU/CPU 百分比分解。

共享模型加载、全部 warmup 和运行总成本单独报告。每臂给出原始秒数、毫秒差和比值，保留全部请求。不得从仪表化 profile 时间推算 clean timing 的“被节省时间”。

### 6.2 固定估计量与精度目标

每个输入 i、会话 s、单元 c 使用 `r_isc = T_QB / ((T_PQ_A + T_PQ_B)/2)`，先在输入间平均 log ratio，再在会话间等权平均；小于 1 表示 QB 更快。A/A 使用 `T_PQ_A/T_PQ_B`，并保留逐输入和逐会话结果。

主估计包含四单元的 log ratio，以及从同一配对数据得到的 lifecycle 主效应、k 主效应、二者交互，共七个预登记对比。报告 session-level t 区间，并对七个对比使用 Bonferroni 同时 95% 区间；所有点估计完整呈现。以日期内均值做 date-level t 敏感性分析，另给逐日期删除结果。会话 t 区间的独立近似不能代替日期敏感性。

实际收益阈值为 **服务时间降低 2%，即 r < 0.98**。精度目标为四单元收益区间半宽不超过约 1 个百分点；该目标需由实测方差检验，不提前编造功效。预算结束仍达不到目标，就报告区间宽和未解决问题，不继续采到显著。

实际收益的强结论要求：资格通过、相应同时区间上界低于 0.98、日期敏感性仍支持阈值、所有会话方向一致，并且点降幅超过该单元最大逐输入 A/A 聚合偏差。区间覆盖零收益表示未解决，不表示等价。只有区间整体落在预定 ±2% 范围内，才能报告该有限面板上的实际等价证据。

## 7. 结果如何改变论文

| 预登记结果 | 论文动作 |
|---|---|
| 同一驱动下 resident k=3 保持实际收益，fresh 或 k=1 的配对效应明显减弱 | 增加受控部署因素结果，用实测交互解释收益如何随合同变化；不再仅并列两个历史面板。 |
| 四单元均有稳定实际收益 | 将正向适用范围扩展到这四个共同合同；原负面板照常保留并解释其历史驱动/输入差异仍未被分别隔离。 |
| 四单元都没有得到实际收益 | 把 QB 的正向加速定位于历史 resident 实现；新结果支持其价值依赖具体运行时。保留修复范围与 draft 盈利性的主要贡献。 |
| k/lifecycle 对比不确定或 A/A 波动过大 | 保持当前“正向 resident、服务增量未解决”的表述；发表精度和所有反转，不追加无上限重复。 |
| 某单元出现真实 reference/work 失败 | 将其列为不合格单元，不报告该单元的合格 speedup；修复数值/状态问题先于继续计时。 |
| Graph 计数随成本变化，但没有随机化/受控 Graph 开关对比 | 报告共同变化，不能把全部成本差归因于 capture、launch 或 replay。 |

如果桥接结果已支持部署结论，停止补实验。只有还要声称“CUDA Graph 是成本差的原因”，才另行登记同一合格单元内的 Graph ON/OFF 对比；仅在两种模式都保持相同 reference 和工作资格时解释该干预。若要把结论扩展到长可见上下文或未见输入，再单独冻结小型 dispatch 边界/未见输入验证；这不是当前稿件大修的前置要求。
