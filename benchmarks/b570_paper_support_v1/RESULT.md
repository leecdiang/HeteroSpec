|轮次|断言测试数|断言失败|实际CPU替代子进程|结论|

两轮合计30个真实 PowerShell 启动器、30个 gated CPU 控制器、22个实际 CPU 替代子进程；两个 unittest 控制器、编译/Git/审查/交付工具另列，不能称为整机全部进程数。科学 native/model/operator 进程仍为0。

第一轮原始通知保存了 `outputs/S0_revision0` 的 action=3，且部分预检查也收到 `sources/actor` 或测试夹具祖先通知。修订将活动输出改成输出根的直接子目录，禁止活动范围外的可变祖先；没有为这些事件增加白名单，也没有唯一归因写入PID。

第二轮失败的日志超限用例，在 CPU 子进程启动前收到：

```
action=3
relative_path=S0_revision1__notification_loss
allowed=false
writing_PID=null
operation_timestamp=null
```

这是前一个已关闭 CPU 槽位的路径。接收时间与完整原始字节都在归档中；通知不提供写入PID或实际操作时刻，不能宣称唯一确定了写入者、操作，或以此追认旧v5原因。正式策略正确拒绝未知事件，但执行环境仍不能可靠到达全部计划控制点。

独立原始审计还发现：第二轮 frozen_input、inactive、sealed_results 的断言虽通过，实际也在子进程启动前被通知提前阻止，未执行预定的修改动作；超限子进程同样未启动，没有ACK/溢出数据。**不能将“16项断言通过”包装成全部负控制完成。** 第一轮的提前终止也逐项保留，见 [INDEPENDENT_S0_RECONSTRUCTION.json](results/INDEPENDENT_S0_RECONSTRUCTION.json)。

实际到达的三个正常路径为 normal、slow_identity、late_panel；实际到达的错误路径包含异常退出、子进程超时、资源读取失败、目录观察超时、模块身份不符、输出截断和注入通知丢失。通知丢失是明确的 CPU parser 故障注入，不冒称观察到真实内核queue overflow。快速退出记录了实际PID/退出，未补造资格。
