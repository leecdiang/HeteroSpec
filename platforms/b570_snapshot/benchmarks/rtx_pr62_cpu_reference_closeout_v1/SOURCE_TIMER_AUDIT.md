## Two measured costs

`close_server.py:measure` starts Python perf_counter immediately before `server.complete(formatted_prompt, cap)` and records wall_ms as1000 times the elapsed seconds after a non-streaming response has been received and parsed. This covers the resident HTTP request, request construction/transport, prompt work, online generation and response handling until client return. It excludes process startup, model load, readiness, the separately saved warmup, GPU_PRE/POST boundary samples, and later server shutdown. It does not certify all asynchronous server cleanup after response delivery. It is request latency for one serial client, not production concurrent throughput.

`tools/server/server-common.cpp:77` exports predicted_ms=`t_gen_ms()`. `server-common.h:352–404` defines it as max(1us, t_gen_last−t_prompt_last)/1000. Prompt timing starts in update_prompt_start; update_prompt_last is called around the first generated sample. Ordinary sampling updates generation end after sampling; the speculative branch updates it after sample/accept and some rollback processing, before later final-token bookkeeping/slot release. This is the original server generation timer, not an independently instrumented sum of all decode components. Draft/verify intervals between those timestamps are charged. First-sample/prompt processing is excluded; final bookkeeping beyond the last update may lie outside this field.
